# SRP Repository Architecture Blueprint

This document defines the release architecture contract for the Semantic Runtime Protocol (SRP) repository.
It is a boundary document, not an implementation change log.

The repository is intended to function as the executable appendix of SRP:

1. `fixed.md` defines the canonical manuscript source for the release pass.
2. `paper/` carries the synchronized manuscript mirror, release snapshot, and supporting reconstruction notes.
3. `srp_runtime/` defines the protocol implementation.
4. `experiments/` evaluates SRP properties under frozen runtime contracts.
5. `artifacts/` stores generated evidence and provenance.
6. `audit/` records claims, evidence mappings, and release governance.

The core principle is simple:

`manuscript != runtime != evidence != artifact != audit`

Each layer may depend on the layer below it, but not the reverse.

## 1. Repository Mission

The repository exists to provide:

- a canonical manuscript source separated from code
- a reference implementation of SRP governance
- reproducible evaluation pipelines
- evidence artifacts with explicit provenance
- an auditable claim-to-evidence record

The repository does not treat experiments as the definition of SRP.
Experiments evaluate SRP properties under frozen runtime contracts.

The repository also does not treat artifacts as raw outputs.
Artifacts are curated evidence objects with a claim status and provenance record.

## 2. Core Layers

The intended dependency direction is:

```text
audit/
  depends on artifacts/
    depends on experiments/
      depends on srp_runtime/
```

This means:

- `srp_runtime/` should not import from `experiments/`
- `experiments/` may call into `srp_runtime/`
- `artifacts/` should be generated by `experiments/` or evidence tooling
- `audit/` should describe and govern the relationship between claims and artifacts

The dependency rule exists to prevent the runtime from becoming aware that it is being benchmarked.

## 3. Runtime Layer: `srp_runtime/`

### 3.1 Responsibility

`srp_runtime/` is the only source of truth for the active SRP implementation.
Its responsibility is to provide the protocol itself:

- state representation
- transition semantics
- authority boundaries
- validation rules
- optimization interfaces
- evidence-aware governance

### 3.2 Expected Contents

Representative modules may include:

- `core/state.py`
- `core/transition.py`
- `core/authority.py`
- `core/evidence.py`
- `core/governance.py`
- `validation/invariants.py`
- `validation/feasible_region.py`
- `optimization/recommender.py`
- `contracts/runtime_contract.py`

### 3.3 Explicit Exclusions

The runtime layer should not contain:

- benchmark runners
- metric aggregation
- report generation
- paper figures
- experiment-specific adapters
- raw result emission

If a module exists to support a paper claim, it does not belong in the runtime layer unless it is part of the protocol itself.

## 4. Validation Layer: `experiments/`

### 4.1 Responsibility

`experiments/` is the validation and evidence generator.
Its purpose is to test SRP properties under frozen contracts and produce reproducible outputs for the paper and audit trail.

### 4.2 Recommended Substructure

The evaluation layer should be organized by paper phase or evaluation purpose, for example:

- `phase_i_observability/`
- `phase_ii_boundary/`
- `phase_iii_optimization/`
- `phase_iv_governance/`
- `phase_v_recovery/`
- `phase_vi_sensitivity/`
- `phase_vii_robustness/`
- `external_validation/`

### 4.3 Required Local Contract

Each evaluation package should, at minimum, make clear:

- which paper claim it supports
- which artifact it generates
- whether the artifact is main, appendix, or archive evidence
- which runtime contract it freezes
- which scorer or metric policy it uses

### 4.4 Explicit Exclusions

`experiments/` should not define SRP itself.
It should not become a second runtime layer.
It should not own the canonical meaning of authority, invariants, or transition semantics.

## 5. Artifact Layer: `artifacts/`

### 5.1 Responsibility

`artifacts/` stores curated outputs that are intended to be cited, audited, or regenerated.
Artifacts are not generic scratch outputs.
They are structured evidence objects.

### 5.2 Proposed Claim Statuses

Artifacts should be categorized as:

- `main`
- `appendix`
- `archive`

### 5.3 Suggested Layout

```text
artifacts/
  main/
    interaction_boundary_enforcement/
  appendix/
    phase_ii_boundary/
    robustness/
    external_validation/
  archive/
```

### 5.4 Artifact Requirements

Each artifact package should contain a minimal provenance bundle, ideally including:

- `metadata.json`
- `manifest.json`
- `config.yaml`
- `metrics.json`
- `trace.jsonl`
- `README.md`

The exact file set may vary, but the provenance must be explicit enough to reconstruct what was generated, when, and under which contract.

## 6. Audit Layer: `audit/`

### 6.1 Responsibility

`audit/` is the claim governance layer.
It records the relationship between paper claims, evidence artifacts, release boundaries, and frozen contracts.

### 6.2 Recommended Files

The audit layer should include:

- `CLAIM_EVIDENCE_MAP.md`
- `ARTIFACT_POLICY.md`
- `RELEASE_CHECKLIST.md`
- `FROZEN_CONTRACT.md`
- dependency maps and role classifications

### 6.3 Audit Rule

Audit documents should answer:

- what claim is being made
- what artifact supports it
- what contract was frozen
- whether the claim is main, appendix, or archive-grade

Audit documents should not silently redefine the runtime.

## 7. Frozen vs Mutable Boundary

### 7.1 Frozen

The following classes of content should be treated as frozen once released:

- runtime contract definitions
- scorer and metric definitions used for paper-facing claims
- claim-to-evidence mappings
- artifact status labels
- release checklist logic

### 7.2 Mutable

The following may continue to evolve:

- new experiment adapters
- new benchmarks
- visualization helpers
- documentation improvements
- compatibility shims

Mutable components must not change the meaning of previously frozen claims without a deliberate release update.

## 8. Role of `srp_experiment/`

`srp_experiment/` is treated as the legacy evidence layer and historical implementation substrate.
It may remain present for reproducibility, but it is not the authoritative runtime source of truth.

In this architecture:

- `srp_runtime/` is the active protocol
- `srp_experiment/` is legacy evidence and compatibility support

This distinction matters because the paper claims SRP as a governance framework, not as a single historical recovery implementation.

## 9. Migration Strategy

The architecture should be adopted in phases.

### Phase 0: Define the contract

Create and maintain:

- this blueprint
- `audit/CLAIM_EVIDENCE_MAP.md`
- `audit/ARTIFACT_POLICY.md`
- `audit/RELEASE_CHECKLIST.md`

No code moves are required in this phase.

### Phase 1: Establish runtime source of truth

Ensure the active runtime implementation is explicitly concentrated in `srp_runtime/`.

### Phase 2: Point experiments at runtime

Move experiment imports toward `srp_runtime/` where appropriate, while preserving compatibility layers if needed.

### Phase 3: Freeze legacy evidence

Document `srp_experiment/` as frozen legacy evidence and compatibility support.

### Phase 4: Archive or retire duplicates

Only after the runtime boundary is stable should duplicate legacy paths be removed or archived.

## 10. Relationship to the Paper

This repository architecture mirrors the paper structure:

- Method defines SRP
- Experiments evaluate SRP
- Appendix A defines evidence governance
- Audit documents map claims to evidence

The repository should therefore read as a reproducible evidence-controlled implementation of SRP, not as a generic experiment dump.
