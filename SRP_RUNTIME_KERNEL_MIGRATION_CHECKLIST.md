# SRP Runtime Kernel Migration Checklist

This document defines the verification gates for migrating SRP from the current experimental runtime into the future runtime kernel architecture.
It is a migration verification document, not an implementation spec.

The central question is:

> What must be true before SRP may safely advance from one migration phase to the next?

This document sits below the adapter plan and above concrete implementation migration.

---

## 1. Migration Gate Overview

Migration should not advance just because code exists.
Each phase must satisfy a verification gate before the next phase begins.

```text
Phase N
  -> Verification
  -> Migration Gate
  -> Phase N+1
```

The checklist is designed to prevent premature architectural commitment and to preserve the evidence generated by the experimental layer.

---

## 2. Phase 0 Checklist - Observation Layer

### Goal

Observe the current runtime without changing behavior.

### Event coverage

- [ ] semantic extraction has a corresponding event representation
- [ ] compression has a corresponding event representation
- [ ] recovery has a corresponding event representation
- [ ] lifecycle change has a corresponding event representation

### Mutation traceability

- [ ] all state mutation paths can be traced
- [ ] mutation source is identifiable
- [ ] drift can be measured from recorded observations

### Safety

- [ ] the original experiment results do not change
- [ ] benchmark output remains consistent
- [ ] the observation layer is non-invasive

### Exit condition

```text
EventStream can describe current runtime behavior without changing it
```

---

## 3. Phase 1 Checklist - Event Wrapping

### Goal

Existing components can produce valid `RuntimeEvent` proposals.

### Producer behavior

- [ ] producers only create events or event proposals
- [ ] producers do not directly mutate kernel state
- [ ] producer output can be inspected independently of mutation

### Event shape

- [ ] `event_type` is valid
- [ ] `schema_version` exists
- [ ] `causal_parent` is present when needed
- [ ] payload fields are complete enough for downstream validation

### Replay preparation

- [ ] event order can be recorded
- [ ] event payload is sufficient to reconstruct the intended transition

### Exit condition

```text
Runtime behavior can be represented as events
```

---

## 4. Phase 2 Checklist - Mutation Routing

### Goal

All semantic mutations pass through the kernel boundary.

### Direct mutation removal

- [ ] `compress.py` does not directly mutate semantic state
- [ ] `recover.py` does not directly mutate semantic state
- [ ] lifecycle managers do not directly mutate semantic state outside the kernel boundary
- [ ] policy layers do not mutate state directly

### Kernel ownership

- [ ] `apply_event()` is the unique mutation entry point
- [ ] invariants are enforced by the kernel before mutation
- [ ] rejected events do not change state

### Exit condition

```text
No uncontrolled state transition exists
```

---

## 5. Phase 3 Checklist - Lifecycle Migration

### Goal

Semantic lifecycle transitions become event-driven.

### Forgetting

- [ ] `Forgotten` event exists
- [ ] recovery pointers or approximation references are preserved when required
- [ ] forgetting outcome is traceable

### Archive

- [ ] archive is distinguishable from delete
- [ ] lineage remains intact after archiving
- [ ] archived content can still participate in replay or attribution when required

### Recovery

- [ ] recovery produces explicit events
- [ ] recovery confidence is recorded
- [ ] recovery can be validated before application

### Exit condition

```text
Semantic evolution becomes event-driven
```

---

## 6. Phase 4 Checklist - Replay

### Goal

The event stream can reconstruct the current semantic state deterministically.

### Determinism

- [ ] initial state plus event stream reconstructs the current state
- [ ] unit identities remain stable under replay
- [ ] relation structure remains consistent under replay
- [ ] lifecycle state can be reconstructed
- [ ] drift summary is reproducible from recorded transitions

### Exit condition

```text
Initial State + EventStream = Reconstructed State
```

---

## 7. Cross-Phase Invariants

These invariants must hold in every migration phase.

### Identity

- [ ] `unit_id` never changes

### History

- [ ] every applied event is recorded

### Attribution

- [ ] every mutation has a source mechanism

### Separation

- [ ] decision, event, and mutation remain conceptually separated

### Replayability

- [ ] phase-specific changes do not destroy the ability to replay or diagnose prior behavior

---

## 8. Migration Block Conditions

Migration must stop or pause if any of the following occur.

### Block Phase 2

- event coverage does not include the main mutation paths
- replay cannot explain observed changes
- benchmark results drift unexpectedly

### Block Phase 4

- event order is not deterministic
- hidden mutation paths remain
- provenance cannot be reconstructed

### General block conditions

- invariants are violated
- observation changes experiment behavior
- the adapter layer becomes a hidden mutation layer

## 10. Scope

This document defines migration gates only.

It does not define:

- callsite mapping
- function-level role assignment
- adapter class implementation
- kernel implementation code

Those belong to later implementation work.
